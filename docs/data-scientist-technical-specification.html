One table you have never seen: how the Data Scientist persona is built

A data scientist installs the kit, loads a dataset or their own file, gets a description of it the kit drafted and they approved - checking the columns where the draft guessed first - (and of how its schema's tables link), checks it is clean, prepares a typed view, explores it with every SQL statement visible, tests one idea with a small model, validates it, asks the data a question with an AI model, shares a result whose numbers they checked and hands the work off in one bundle - nine numbered steps across four notebooks, and never a terminal. This page describes what the kit does at each step, as the code on this branch does it.

Everything the user does happens in a notebook that opens already connected, with no password in it. The column map (the descriptor) is proposed by the kit from a profile of the data, shown with the guesses first, checked against the data and approved by the user; every later step reads it, which is why changing one assignment, DATASET = ..., moves every notebook to another dataset. A table that is one of several gets a schema map too - the schema's tables and how they link - and the notebook can turn it into one joined view. The ML Engineer persona is switched off on this branch (kept, not removed) so the work can focus here.

How a dataset reaches the database

  1. exakit data-load fraud_transactions (or the quickstart's load cell) downloads fraud_transactions-2026-11-06.tar.gz and checks its SHA-256 against manifest.json.
  2. Every CSV in it is checked against its own digest, then loaded with exapump into the dataset's schema by its 01_create_schema.sql.

04The column map (descriptor)

The kit profiles the table (type, share of empty cells, distinct values, date span, text length, and the shape of each text column's values), proposes a role for every column with the evidence that chose it, and the user corrects and approves it in a picker - no YAML to edit. The picker shows the columns drafted at low confidence first, under Check these first, then the rest.

Column roles

key, time, measure, category, flag, text, identifier, other - one per column.

Slots the notebooks read

key, time (date), target (label), category, entity, text. An empty slot carries its reason, and the steps that need it skip and print that reason.

How a role is chosen

One profiling pass reads three things per column, and the first rule that matches wins (setup/lib/descriptor/roles.py, every threshold pinned by a test):

SignalWhat it settlesExample
the typedates and timestamps are time; a decimal with a scale is a measure however few values it hasL_DISCOUNT (11 values) → measure
the numbersno nulls and all distinct → key; two values → flag; one value → other; ≤ 50 values → categoryCURRENCY (one value) → other
the value shapeone token holding a digit is a code → identifier; three words or more → text; a date pattern → time; e-mail, phone, IBAN, postcode → sensitiveSKU-1042, B09KXVBD7Z → identifier
the name, lastonly settles what the numbers leave open; never overrides a clear shapeQTY (10 values) → measure, O_CUSTKEY → identifier

A unique column is a key only when it is an integer, or text that is code-shaped or named like a key - so an e-mail, an IBAN or ten country names in a ten-row table are never keys. Sensitive also by name: a postcode name with postcode-shaped values, a person's name (CUSTOMER_NAME, DRIVER_NAME), a street address. Confidence is low wherever the draft is a guess, so the reviewer reads those first.

How good the first draft is

tools/descriptor_benchmark.py scores a fresh draft against a reviewer's answers: the kit's 15 dataset tables, 5 synthetic tables shaped like common data (customers, order items, sensor readings, employees, loans), and 5 held-out tables written after the rules and never tuned to. A column where two roles are both right lists both.

ScoreBeforeNowHeld out, first run

The held-out tables' two misses - account_id read as an amount ("acccount"), and DRIVER_NAME not marked sensitive - were fixed after that run and are recorded in the tool; all held-out scores are 100% now. tests/test_descriptor_benchmark.py fails when any score falls under its floor.

Draft, approve, version

  • A draft is enough to explore. Ask your data and Share call require_approved and refuse a draft, saying how to approve it.
  • Approving writes v<n>.yaml and current.yaml under ~/.exasol-starter-kit/descriptors/<SCHEMA.TABLE>/; a version file is never rewritten.
  • The roles are published as a view, EXAKIT_SEMANTIC.<SCHEMA>__<TABLE>, whose column comments carry them; agents read the roles from there over MCP.
  • Approving roles that the current version already has writes nothing and says where that version is stored (and the view, when it exists).
  • Approving looks at the data first (setup/lib/descriptor/review.py, at most three SELECTs). Refused, with what to change: a key slot whose column repeats or has a gap now; a target that does not hold exactly two values. Warned, and approved: a column that gives the target away (the Explore notebook's leakage rule), and the low-confidence roles approved as drafted, by name - approving them is a decision the approver should know they made.

The column map describes one table. How the tables of a schema fit together is a second, smaller document beside it, the schema map.

Written as jupytext percent-format .py files, built into .ipynb and Marimo versions by tools/notebooks.py. The four are one path: nine numbered steps, the day's work of a data scientist, each a ## Step N heading with a three-line plain explanation of what happens there and ### parts under it. Every notebook's first cell says which steps it holds and shows the whole journey, so a reader always knows where they are. Each important idea is explained the first time it appears: what it is and why it is used.

The kit, from a notebook

Nothing on the path needs a terminal. nb.kit_check() prints what is installed and running (the database, each add-on and its address, the datasets loaded). nb.exakit("update"), nb.exakit("marketplace", "dash-server"), nb.exakit("data-load", "walmart_sales"), nb.exakit("logs") - any command of the kit - run the same exakit the terminal runs, with the output streaming into the cell as it happens and the exit code in the result (run.ok). nb.addon_ready("dash-server") installs an add-on when it is missing and starts it when it is stopped, which is how Share gets Dash Server. The command runs detached from any terminal, so a question it would ask takes its default; a choice goes in up front (env={"EXAKIT_MCP_CLIENTS": "claude"}). Nothing is ever typed into a prompt from the notebook.

The hand-off bundle

nb.handoff_bundle(connection, dataset) writes ~/.exasol-starter-kit/bundles/<workflow id>/ and a zip beside it: README.md (what the data is, the column-map version the numbers rest on, the questions approved, the dashboards published, how to repeat it), descriptor.yaml, schema-map.json when there is one, queries.sql (every distinct statement the workflow ran, with its SHA-256 and row count) and workflow.jsonl. The log gets a handoff line with the path. It works without Dash Server, and never holds a password.

06How every cell follows the data

No notebook names a column or a table. Six rules hold that:

  1. One assignment picks the data. DATASET = None means "the dataset approved last in a quickstart" (nb.chosen_dataset), else amazon_sales; any id or a file path with its descriptor beside it also works.
  2. Columns come from roles. dataset.col("category"), dataset.col("label"), ... and dataset.fact_table; a role the data does not have is None, never guessed.
  3. Result columns are named after the data. nb.name() and nb.count_name() turn CANCELLED into CANCELLED_PCT and the grain into ORDER_LINES or TRANSACTIONS; Share's query, title and app name follow the same rule.
  4. Every name says what it holds, and is set once. dataset, connection, workflow_id, LABEL_COLUMN, COUNT_HEADER, feature_values - no ds or X - and no cell reassigns a name another cell set, so Marimo runs the same cells without renaming anything.
  5. The prepared data is just another dataset. The joined and the typed view each get their own approved column map, so dataset - the name every step below Prepare reads - is the table as loaded, its joined view or its typed view, and the cells do not change. USE_JOINED and USE_PREPARED in the first cell choose; both False by default, so nothing is created unasked.
  6. A missing role skips, with its reason. No date (fraud_transactions): no trend, and the model leaves the month out. No text (all three): the text step skips.

Two tests hold this: SwapTest renders every SQL f-string for two datasets and requires them to differ only in descriptor values, and MissingRolesTest removes each role in turn and requires every step that needs it to skip, not fail.

A typed, cleaned view

The checks only report. nb.typed_view(connection, dataset) turns what they found into one proposed view, read from the values (one aggregate statement over all the text columns) and shown with its exact SQL before anything exists:

WhatRule
a number written as textevery value parses → DECIMAL(p,s) sized to the values; a leading zero, or a name that says code, id, zip, phone, SKU and the like, keeps it text
a date or timestamp written as textevery value parses in one of the known formats → DATE / TIMESTAMP in that format
true/false written as text→ BOOLEAN
blanks and placeholders→ NULL (the placeholders the checks found)
exact copiesjudged on the cleaned values: the first by the key is kept (ROW_NUMBER()), or SELECT DISTINCT without a key

Identifiers and columns that are already typed are left as they are. With USE_PREPARED = True (or create()) the view goes into EXAKIT_PREPARED as <SCHEMA>__<TABLE>, gets its own approved column map with the same roles (a date found in text fills an empty time slot) and becomes the dataset every later step and notebook reads. A table that needs nothing says so and stays as it is. On fraud_transactions it turns the two placeholders into NULL and drops 885 copies.

08Several tables: the schema map

A fact table rarely stands alone: orders point at customers, customers at a country. The schema map describes the whole schema the way the column map describes one table - every table with its rows and key, and every link between them with the evidence that found it - and is drafted, corrected and approved the same way.

exakit describe --schema TPCH                                   # draft: tables, keys, links
exakit describe --schema TPCH --approve --unlink ORDERS.O_CLERK # correct and approve
exakit describe --schema SHOP --approve --link ORDERS.CUST_REF=CUSTOMERS.ID

How a key and a link are found

  1. Key. A declared primary key; else the first column named like a key (ID, …_ID, …KEY) that is unique and never empty, counted in one statement per table.
  2. Declared link. A foreign key the database lists (EXA_ALL_CONSTRAINT_COLUMNS) is taken as it is.
  3. Found link. A column that names another table's single-column key - the same name once a short table prefix is taken off (O_CUSTKEY and C_CUSTKEY), or CUSTOMER_ID against CUSTOMERS.ID - of the same kind (number or text), and whose every non-empty value is in that key: one LEFT JOIN each, at most 0.1% missing. A name alone never makes a link.

Every link is many-to-one: the key side is unique, so following it adds columns to a row and never adds rows. Only SELECTs run while the map is drafted.

Approve and publish

  • The draft is kept in ~/.exasol-starter-kit/descriptors/<SCHEMA>/draft.json; approving writes v<n>.json (never rewritten) and current.json, with the owner and time. A link to a table or column the schema does not have is refused; approving what the current version says writes nothing and says where it is.
  • The links are published as a view any read-only client can query, EXAKIT_SEMANTIC.<SCHEMA>__RELATIONS (FROM_TABLE, FROM_COLUMN, TO_TABLE, TO_COLUMN, KIND, EVIDENCE), granted to the MCP user. The schema's own tables are never altered. A publish that fails leaves the approval standing and says why.

One joined view, in Explore

schema_map = nb.describe_schema(connection, loaded_dataset)      # the tables and links, as found now
joined_view_proposal = schema_map.joined_view(loaded_dataset)    # this table + every table its links reach
joined_dataset = joined_view_proposal.create(connection) if USE_JOINED and joined_view_proposal.needed else loaded_dataset

The proposal follows links from the main table up to three steps, each a LEFT JOIN (no row is lost when a value has no match), and shows every join and the SQL. A joined table's key is left out (the side it came from holds it); a column name used by two tables is prefixed with its table. A table reached along two paths is joined once per path and its columns named after the path: on TPC-H's LINEITEM the supplier's country is SUPPLIER_NATION_N_NAME and the customer's is ORDERS_CUSTOMER_NATION_N_NAME. create() approves the map if it is a draft, creates EXAKIT_PREPARED."<SCHEMA>__<TABLE>__JOINED" and gives it its own approved column map with the main table's roles and slots carried over (id <dataset>_joined), so the typed view, the model, Ask and Share all read the joined data. A table that links nowhere has nothing to join and says so.

Correct the map in the notebook before creating anything: schema_map.unlink("ORDERS.O_CLERK"), schema_map.link("ORDERS.CUST_REF", "CUSTOMERS.ID"). Each correction is checked against the schema's tables and columns, and marked "set by you" as its evidence.

09Validate: leakage and baselines

nb.leakage_check(connection, dataset) looks at every column with at most 50 values (not the key, identifiers or text) and flags one whose values almost decide the label on their own: values where the label is at least 99% one way cover at least 95% of rows and catch at least 90% of the label-1 rows. Such a column was usually written after the outcome. The model leaves it out.

- STATUS gives CANCELLED away: CANCELLED is 1 whenever STATUS is 'Cancelled'.
  It was probably written after the outcome - leave it out of any model.

The same rule runs earlier too: approving a column map with a target set warns about such a column (STATUS gives CANCELLED away: CANCELLED is '1' whenever STATUS is 'Cancelled'), so it is seen before any notebook trains on it.

The model's score is ROC AUC on a quarter it has not seen, with a note in plain words ("about as good as guessing" near 0.5). A rare label is called out in Prepare, so accuracy is never the measure.

10The small model

A one-hot logistic regression with balanced class weights and a stratified, seeded split (random_state=0), on this computer. Its features are what the map names and the leakage check allows:

  • the category and the entity, as text;
  • the month of the date, only when there is a date.

With a date it reads the newest 20,000 rows; without one, the first 20,000 by the key - the same rows on every rerun either way. It needs a label and a category or entity. The Model clues cell lists the values the model leans on each way, at most half of them per side, so no value appears on both.

11Ask your data

  1. A question in plain English. With DRAFT_WITH_MODEL = True the user's own model drafts SQL from the approved map (every column with its role, evidence and note; no rows are sent); otherwise a starter query built from the roles.
  2. The proposal shows the SQL one clause per line, what the model assumed and what to check. Nothing has run.
  3. proposal.approve() fixes the exact text (its digest is logged); proposal.run() refuses anything else.
  4. It runs through the MCP server beside the database, as the read-only user: one SELECT or WITH, at most 1,000 rows. A draft map is refused.

12Share a checked result

The share notebook counts rows by the category (else the entity, else the label), named after the data, and builds a Dash Server dashboard from that one visible query:

  1. nb.share(dataset, dashboard_query, dashboard_title, app_name) prepares a draft carrying the query digest and the descriptor version.
  2. dashboard_draft.preview(...) publishes a preview the user opens and compares with the SQL.
  3. dashboard_draft.confirm(..., figures_checked=True) publishes it only after the user says the figures are checked.

Needs exakit marketplace dash-server and exakit start dash-server (port 5100 by default).

13Lineage: the workflow log

The quickstart starts a workflow (wf-YYYYMMDD-xxxxxx); Explore, Ask and Share continue it on their own with nb.continue_workflow() - this kernel's workflow, else the one inherited through EXAKIT_WORKFLOW_ID, else the last one started on this machine (~/.exasol-starter-kit/last-workflow) - so there is no id to copy or paste. Each SQL statement (with its digest and row count), each descriptor draft and approval, each approved question and each trace is one line in ~/.exasol-starter-kit/workflows/<id>.jsonl, in order; exakit workflow show <id> prints it. Running a quickstart again starts the next piece of work.

14AI agents through MCP

Every AI client the kit connects (Claude, Claude Code, Codex, Cursor, VS Code Copilot, Gemini CLI, OpenCode, Continue) reaches the database through one MCP server: the official Exasol MCP server that the Exasol Personal launcher runs beside the database, at http://127.0.0.1:4896/mcp, connected as the dedicated read-only user. Client configs hold the URL and no password; Claude Desktop goes through uvx mcp-proxy.

Agents read the approved roles from EXAKIT_SEMANTIC.<SCHEMA>__<TABLE> and the approved links from EXAKIT_SEMANTIC.<SCHEMA>__RELATIONS, so a question that needs two tables is answered from an approved join, not a guessed one.

There is no fallback server. When it does not serve, exakit mcp-setup and exakit mcp-doctor heal it:

CaseWhat the kit does

15Your model and Langfuse

Explore and Ask open with an optional cell: fill in MODEL_ID, PROVIDER_BASE_URL (any Chat Completions endpoint, a local one too) and LANGFUSE_BASE_URL, run it, and the keys are asked for in a hidden prompt. They stay in the notebook's kernel only - never in the file, its outputs or on disk. Left empty, the cell changes nothing; exporting the same variables before exakit notebook still works. A key is never sent over plain http:// to another machine.

16Credentials and safety

  • No host, user or password in any notebook, helper or output template; a test greps every shipped file for them.
  • Notebooks connect from the kit's store; passwords live in files under ~/.exasol-starter-kit/credentials/.
  • The database certificate is pinned (trust on first use) for every kit-built client.
  • AI clients reach the database only as the read-only user; writes are rejected by the database itself.
  • No SQL from Ask runs before the user approves that exact text.

19Known limits

  • Licences of the three datasets are not confirmed.
  • No dataset has a text column, so the text step (and its Langfuse trace) is exercised only on the user's own data.
  • Share needs Dash Server running; it was not part of the live run above.
  • The schema map finds single-column keys only, and follows links many-to-one; a live source's schema (a virtual schema) is not surveyed, since every count would be a round trip to it.
  • The hidden prompt of the settings cell is shown by Jupyter; in Marimo it may not appear, and the cell then says how to set the key in the terminal.
  • The benchmark's answers are one reviewer's judgement; where two roles are both reasonable, both count. Its five held-out tables scored 98.1% on their first run and were then fixed, so they are no longer unseen.
  • A column map approved before these rules keeps its roles (an approval is never rewritten); in a notebook, exakit_nb.describe("SCHEMA.TABLE", force=True) drafts it again for review.
  • Approving a live source's column map (a virtual table) does not query it: the key and target checks and the leak warning are skipped; the low-confidence list is still shown.
  • The ML Engineer persona is switched off on this branch; its notebooks and training code stay.

20Troubleshooting

A step says "Skipped - … needs the date role".
The data has no column for that role (no date in fraud_transactions). It is a fact about the data, not an error.
"slots.key: … repeats" or "… is empty in … rows" when approving.
The column in the key slot does not name one row each in the table now. Pick a unique, never-empty column, or leave the key empty (--role key=-; in the picker, —).
"slots.target: … holds N values; a target is a yes/no outcome".
The target must hold exactly two values (0/1, true/false, two labels). Pick such a column, or leave the target empty.
"Warning: … gives … away" after approving.
That column decides the target on its own and was probably written after the outcome. The approval stands; leave the column out of any model (Explore's model does).
"Warning: N role(s) drafted at low confidence were approved as drafted".
Those are the columns the draft guessed. The approval stands; check them in the picker (they are listed first) and approve again if one is wrong.
"training needs an approved descriptor: … is a draft".
Approve it in the quickstart's review cell, or exakit describe <id> --approve.
The schema map has a wrong link, or misses one.
schema_map.unlink("TABLE.COLUMN") or schema_map.link("TABLE.COLUMN", "TABLE.KEY") in Explore; --unlink / --link with exakit describe --schema <SCHEMA> --approve. A link the data does not hold (more than 0.1% of values missing) is not found on its own - declare it or add it by hand.
"… links to no other table: there is nothing to join".
The table has no column that names another table's key. Its data is used as it is.
Ask fails with "The Exasol MCP server … did not answer".
Run exakit mcp-doctor: it heals the server beside the database and says what it could not fix.
Share says Dash Server is not installed, or stopped.
Run the Dash Server, from this notebook cell: nb.addon_ready("dash-server") installs it when missing and starts it when stopped, with the log in the cell. Anything else the kit can do runs the same way: nb.exakit("...").
The dataset download fails offline.
Point EXAKIT_DATASETS_MIRROR at a folder (or an https URL) holding the archive.

22Glossary

Descriptor (column map)
The approved description of one table: every column's role with its evidence, and the slots the notebooks read.
Schema map
The approved description of a schema: its tables with their keys, and the links between them with their evidence.
Many-to-one link
A column whose values are another table's key (an order's customer number); following it adds that table's columns without adding rows.
Joined view
One table with every table its links reach, as one view with its own column map.
Typed view
The table with numbers and dates in their types, placeholders as NULL and copies dropped, proposed from the values.
Confidence
High or low: low where the draft is a guess (a number near its threshold, a role from a name alone). Every role the benchmark's reviewer disagreed with was marked low.
Slot
One of key, time, target, category, entity, text: the column a notebook step reads for that purpose.
Leakage
A column that knows the outcome because it was written after it; it makes a model look perfect and fail on new rows.
Baseline
The simplest answer a model has to beat, such as always predicting the common class.
ROC AUC
How often the model ranks a label-1 row above a label-0 row: 0.5 is guessing, 1.0 is perfect.
Sidecar
A container the Exasol Personal launcher runs beside the database; the MCP server is one.
Hand-off bundle
One folder and zip with the approved column map, every query that ran, the dashboards and the workflow log, so a colleague can repeat the work.
Workflow
One id that links the queries, descriptor versions, approvals and traces of one piece of work.
