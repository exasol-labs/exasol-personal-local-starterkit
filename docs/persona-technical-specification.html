Persona Technical Specification

Exasol Personal Local Starter Kit · kit 0.3.0 · skills 1.24.30 · branch staging-vs-preproc-persona-rc-build · written against commit 95e32e66 on 13 November 2026.

How a persona is built, end to end: from the install one-liner to the guided cards a Data Scientist clicks, and everything in between. Every statement names the file, function or variable it comes from, so it can be checked against the code. Where something could not be confirmed from the code, it says so.

How to read this

  • New to the kit: read At a glance, Glossary and Architecture, then the Install flow.
  • Answering a question: use the navigation on the left; each section starts with what the part is for, then the mechanics, then where it lives.
  • Changing something: go to How to change things; it lists the files to touch and the tests that will fail if a rule is broken.

Paths are relative to the repository root. ~/.exasol-starter-kit is the kit home ($EXAKIT_HOME). In flow diagrams the top colour says who acts:

At a glance

A persona is a named set of answers the installer already accepts: which datasets to load, which AI clients to connect, which marketplace add-ons to install, which services to start. It is a JSON file in personas/. Choosing one at install time (or later with exakit persona add) turns those answers into a ready workspace. The Data Scientist persona is the one with the deepest build: four add-ons, four notebooks with guided cards, a column-map workflow and a semantic layer.

Architecture

Entry · install.sh / install.ps1 → setup/setup-macos.sh (or -linux.sh, -windows.ps1) → setup/lib/common.sh + persona.sh + twins in *.ps1
Command · exakit (setup/exakit, setup/exakit.ps1): every user-facing command; Python services under setup/lib/*_service.py and marketplace/*.py
Database · Exasol Personal from the launcher (exasol), on 127.0.0.1:8563, TLS pinned; BucketFS; sidecar MCP server on 127.0.0.1:4896
Add-ons · marketplace/addons/*.py driven by marketplace/service.py and apply.py; versions pinned in versions.json
Data layer · exakit data-load (exapump), exakit connect (virtual-schemas engine), exakit describe (describe_service.py + setup/lib/descriptor/)
Notebooks · notebook venv with exakit_nb (alias exakit.nb) and exakit_guide (alias exakit.guide); JupyterLab and Marimo as on-demand services
AI · AI clients over MCP (read-only); the notebook model via an OpenAI-compatible endpoint the user configures; optional Langfuse tracing

Two rules shape the whole build:

  1. One code path. A guided card runs the exact cell text of its notebook (actions.py), and the notebook cell calls the same exakit.nb function the terminal command uses through the kit's service. ParityTest in tests/test_notebook_guide.py fails when a card calls something no cell calls.
  2. No secret in sight. No host, user or password is ever in a notebook (test_no_shipped_file_holds_a_connection_value); passwords travel in files or on standard input, never as an argument; AI models are never shown a row.

Install flow

The one-liner

curl -fsSL https://www.exasol.com/install/starter-kit.sh | sh          # macOS, Linux
irm https://www.exasol.com/install/starter-kit.ps1 | iex                 # Windows

install.sh takes EXAKIT_REPO (default exasol-labs/exasol-personal-local-starterkit) and EXAKIT_REF (default main), downloads https://github.com/$EXAKIT_REPO/archive/refs/heads/$EXAKIT_REF.tar.gz (falling back to refs/tags/), sends a GITHUB_TOKEN header through curl -K - on standard input for a private repository, unpacks into $EXAKIT_HOME/kit, and records EXAKIT_KIT_SOURCE (REPO@REF, or local:<path> with EXAKIT_LOCAL_KIT). EXAKIT_KIT_SHA256 pins the archive digest.

EXAKIT_VERSION_POLICY: manifest (default: the tested set in versions.json), latest (resolve each component upstream), anything else = pinned (built-in fallbacks, no network). A single component can be pinned with EXAKIT_<COMPONENT>_VERSION.

Validation is problems() in setup/lib/persona_service.py:

An empty list means the "nothing" word for that key. An invalid file is skipped and named on stderr; dotfiles are ignored; a UTF-8 BOM is fine.

Combining several personas

combined(): all wins; the nothing-word applies only when every persona says it; otherwise lists are unioned in kit order. answers() emits a variable only when the user left it unset (datasets → EXAKIT_DATASETS, mcp_clients → EXAKIT_MCP_CLIENTS, addons → EXAKIT_MARKETPLACE_ADDONS, notebook_tools, udf_language). Datasets all becomes the bundled ids, none becomes EXAKIT_LOAD_SAMPLE=0; udf_language comes from the first persona that has one; the output ends with EXAKIT_PERSONA=<ordered ids>. For addon_reasons the first persona with a reason wins. selectable() refuses a hidden persona unless it is already recorded.

exakit data-load

cmd_data_load() in setup/exakit, engine setup/lib/exapump.sh (exapump upload <file> --table <schema.table>).

  • A file loads into ${EXAKIT_SCHEMA:-STARTER_KIT}.<TABLE>; the table name is the upper-cased file name (exakit_table_name_from_path), or EXAKIT_DATA_TABLE. A folder loads one table per file.
  • Kinds: csv (.csv; .tsv/.txt refused by name), parquet (.parquet/.pq), json (.json/.geojson/.ndjson/.jsonl); compressed (.gz/.bz2/.zst/.xz) resolve to the inner kind. exakit_csv_inspect finds the delimiter and flags BOM and CRLF.
  • JSON goes through the json-tables add-on: normalised to NDJSON, shredded to Parquet, loaded the same way.
  • Excel is handled by the notebook path only: exakit_nb/spreadsheet.py writes one sheet to CSV beside the file, converts Excel day numbers, and writes a UTF-8 copy of a non-UTF-8 CSV.

External sources (virtual schemas)

A source is read live: nothing is copied. Each is one virtual schema VS_<NAME> with a CONNECTION EXAKIT_SRC_<NAME> holding the credential inside the database.

Column maps

A column map says what each column means, so every later step can use the data without guessing. The kit drafts it from measurements; a person approves it; the approval is versioned and published to the semantic layer.

Roles and sensitivity

RoleMeaning
keydifferent in every row
timea date or time
measurean amount to add up or average
categorya short list of repeated values to group by
flagexactly two values; can be the target
textsentences people wrote
identifiera name or code pointing at one thing
otherleft out

descriptor/roles.py classify() decides sensitivity first, then rules in order (first match wins). Thresholds: SENSITIVE_SHARE 0.90, DATE_SHARE 0.98, TEXT_AVG_LENGTH 40, CATEGORY_DISTINCT 50, CATEGORY_RATIO 0.02, IDENTIFIER_RATIO 0.9, NEAR 0.10. Confidence is high or low (low within 10% of a threshold, or decided by name only). A column is sensitive when ≥90% of values are email, phone, IBAN or postcode, or its name says postcode/ZIP, a person's name, or an address: it becomes an identifier, its profile keeps counts only, and it is never charted or sent to a model.

Profiling (descriptor/profile.py)

Shape from EXA_ALL_COLUMNS (schema_digest = SHA-256 of NAME:TYPE lines). A virtual table (an external source) is read once, its first 10,000 rows in one statement, and profiled in Python with profile_rows (the same numbers a file gets), so the remote system answers one query. A local table: batches of 40 columns: COUNT, APPROXIMATE_COUNT_DISTINCT, MIN/MAX, AVG(LENGTH) and REGEXP_LIKE pattern counts (iso, dotted, slash, email, phone, iban, postcode, code, number, words, nodigit, postal); then top values for low-cardinality non-sensitive columns, exact distinct counts near the row count, and date ranges. Over 30 s is flagged slow.

Draft and slots (descriptor/draft.py)

Slots: key (a key-role column, identifier-named first), time (fewest nulls), text (named as text, then longest), target (never drafted: the person's question), category (a 2–20 value string, grouping names first), entity (more than 20 distinct, at most one per two rows). slot_evidence says why a slot is empty. Document: {descriptor, dataset, source{kind, object, schema_digest, profiled_rows}, version, status, grain, slots, slot_evidence, columns{role, confidence, evidence, sensitive, note}}.

Approval (descriptor/flow.py approve, review.py)

  1. Rules: key slot needs role key, time needs time, text needs text; no sensitive column in target, category, entity or text; every live column has a role.
  2. The live schema_digest must match.
  3. Data review: refused when the key has nulls or duplicates or the target is not exactly two values; a leakage warning for a column whose values give the target away (≥99% one way, covering ≥95% of rows); low-confidence roles nobody changed are warned. A virtual source skips the data checks.
  4. Writes v<n+1>.yaml (exclusive create), status approved, owner, approved_at; replaces current.yaml atomically.
  5. Publishes to the semantic layer (a failed publish leaves "approved, not published" with the retry command).
  6. Writes a describe.approve workflow line.

Approving what the current version already says writes nothing. Store: descriptors/<SCHEMA>.<TABLE>/{v<n>.yaml, current.yaml, draft.yaml, profile.json}; schema maps in descriptors/<SCHEMA>/. Notes (note) are a column's description; role_review.approve(..., notes={COLUMN: text}) saves them, at most 300 characters each.

Build rules (descriptor/semantic_model.py)

  • Each table → an entity (aliases t1…; name is the table, or SCHEMA_TABLE on a clash). Names via identifier(): lower snake case, never an SQL keyword, at most 100 characters.
  • The key → a PRIMARY unique key. A link target that is not the key gets a <entity>_<col>_uk UNIQUE key (Semantic Views requires a unique key on the "one" side).
  • A link → a MANY_TO_ONE LEFT relationship <a>_to_<b> with its key mapping.
  • time, category, flag (not sensitive) → dimensions; a DATE/TIMESTAMP also gives <col>_month.
  • measure → fact (non-numeric cast to DOUBLE; sensitive → PRIVATE).
  • Every entity gets a private row fact <entity>_row = 1 and the metric <root>_count = SUM(row) (COUNT(*) is not allowed). Each public fact gives total_<fact> (SUM) and average_<fact> (total / NULLIF(count,0)).
  • One semantic view per root: tables with measures first, then uncovered tables; dimensions from entities reachable along exactly one many-to-one path (depth 3).
  • The description ends with [built by exakit]; a model of the same name without it is never touched. Published as SEM_<MODEL>; a schema's own model is named after the schema.

Statements: EXECUTE SCRIPT SEMANTIC_ADMIN.CREATE_MODEL / ADD_ENTITY / ADD_UNIQUE_KEY_WITH_COLUMNS / ADD_RELATIONSHIP / ADD_RELATIONSHIP_KEY_MAPPING / ADD_CUSTOM_EXTENSION / ADD_SEMANTIC_OBJECT / APPLY_SEMANTIC_DEFINITION_OR_FAIL / PUBLISH_MODEL.

AI proposals

describe_service.semantic_ai() (needs EXAKIT_MODEL_ID and EXAKIT_PROVIDER_BASE_URL) sends one call with names, types, grains, notes and a category's top values only, never a row or a sensitive column. sm.ai_accept() keeps labels (display, comment, synonyms) and at most 8 metrics, each checked: ADDITIVE must be SUM of a public fact of that view; DERIVED/RATIO arithmetic over that view's metrics; a filter only on a known dimension value; type DOUBLE or DECIMAL. A refused metric is named with its reason; Semantic Views validates it again when applied.

Refresh

Every approval updates the schema's model (publish_schema) and every multi-source model that lists the table (refresh_including). exakit describe --model N --refresh / nb.refresh_semantic does it for one from its kept inputs.

In place, not rebuilt (sm.changes / sm.apply)

semantic/<model>.json keeps the spec last published. sm.changes(previous, spec) returns the statements that turn one into the other: ADD_ENTITY + key for a new table, ADD_UNIQUE_KEY_WITH_COLUMNS for a new link target, ADD_RELATIONSHIP + key mapping + evidence for a new link, APPLY_SEMANTIC_DEFINITION_OR_FAIL for a new or changed view, then one PUBLISH_MODEL; [] when nothing changed; None (rebuild) when anything is taken away, a key or source moves, or the name or description differs. Link discovery

Tables from different sources rarely declare how they join, and the same thing is often named differently. descriptor/links.py find() finds links from the values, with bounded statements only, and never joins two sources while searching.

  1. Read the columns and declared keys; merge approved keys.
  2. One aggregate per table. Text longer than 200 characters is prose and excluded. A key is "measured" when every value is present and the approximate distinct count is ≥0.9 × rows (rows ≥ 20).
  3. Candidates (fits): same kind; never a measure, flag, time or text role; a number must sit inside the key's range, span ≥50% of it, and be backed by name similarity ≥0.5, an approved key/identifier role, or a proposal.
  4. Score by name similarity; AI or user proposals first. At most 400 pairs (MAX_CHECKS).
  5. Sample 500 distinct values and count how many are in the key.
  6. Text with ≥50% found is counted by rows: ≤0.1% unmatched rows → high, else partial (never joined). Numbers with ≥90% found → low: a sequence matches by chance, so only a person's tick uses it.
  7. One link per column; a measured key is confirmed unique exactly.

only=[tables] limits the search to a selection; with same_schema=True two tables of one schema are compared too (the card does this). check=["A=B"] tests a pair someone has in mind and returns it with its evidence or under rejected.

A bare exakit at a terminal opens a Textual app, setup/tui/exakit_tui, with five tabs: Status, Marketplace, AI clients, External sources and Personas. exakit tui [--tab status|marketplace|clients|sources|personas] [--persona ID] opens it on a tab, and exakit <persona-id> on that persona's page. The launch decision is exakit_tui_wanted (setup/lib/tui.sh, twin Test-ExakitTuiWanted in tui.ps1): stdin and stdout are a terminal, not CI, TERM is not dumb and EXAKIT_NO_TUI is not 1. Otherwise a bare exakit prints the help, exakit <persona-id> prints persona show, and exakit tui exits 2 naming the --json commands to use.

Docs site

notebook/docs: Next.js + Fumadocs static export (basePath /docs), Mermaid diagrams with clickable nodes. Sections: kit, data-scientist (set-up, get-the-data, explore, prepare, model, evaluate, communicate, monitor, development), security. tools/nb_docs.py generates the reference from docstrings and the command table from setup/help/exakit.json; then npm run build, tools/nb_docs.py --publish (to site/, stamped in BUILD.json), --check. nb.docs() serves it on 127.0.0.1, ports 8790–8809 (EXAKIT_DOCS_PORT first), reusing another kernel's server. exakit docs [topic] [--print] [--json] opens it from a terminal.

Update and uninstall

exakit update [<component>…] [--yes] [--json] updates the kit scripts, exapump, MCP, pyexasol, skills and installed add-ons; a database or runtime change needs consent; pending core tasks re-run the installer once without questions. exakit update exakit picks up persona and catalog changes and re-syncs the notebook helpers.

exakit uninstall [<addon>] [--dry-run] [--yes]: a bare run opens a menu ending in a typed UNINSTALL gate. Order: boot entries, add-ons outside the kit home, the database and all data, managed MCP configs, skills the kit placed, exapump profiles, the kit home, CLI binaries. Kept: notebooks/, mlflow/, the dash-server instance (unless EXAKIT_UNINSTALL_NOTEBOOKS=remove), uv, the PATH line.
